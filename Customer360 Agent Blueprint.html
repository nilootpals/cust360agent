The big picture

Four tiers, one Python file in the middle

An AI agent is an ordinary application with one unusual component: a language model that decides, step by step, which of your functions to call. Everything else is familiar engineering: a UI, an API, a database, and scheduled jobs.

Notice the two paths through the server. The dashboard and shortcuts use fixed SQL and never touch the LLM, so they are instant and free. Only the chat uses the agent path, where the LLM writes its own queries through tools.

Data layers

Why a semantic layer matters more than the model

The database has three layers, each built on the one below:

Raw data (base tables)

What the bank’s systems record: holding, account, fixed_deposit, customer_transaction. Accurate but low-level: mixed currencies, no business definitions.

Semantic layer (views)

Plain SQL views such as vw_investor_profile join tables and add business labels (risk profile, investor type). They are always live because they compute on every query.

Analytics layer (materialized views)

Pre-computed results stored as tables, such as mv_customer_360: everything converted to SGD, derivatives counted at their real exposure, rate-hike impact already calculated. Refreshed nightly with refresh_analytics(). Each metric is defined once in metric_catalog, so the dashboard and the agent always agree.

Rule of thumb: if a number matters to the business, compute it in SQL you have tested, and let the LLM select it rather than derive it.

Tools

The agent can only do what its tools allow

A tool is a Python function the LLM may call. LangChain sends the model each tool’s name, docstring and argument types; the model replies with “call run_sql with this query” instead of text. Your code runs the function and hands back the result. Four small, well-described tools are enough here.

ToolWhat the LLM uses it forWhat it doesGuardrail
list_objects()“What data exists?”Lists allowed views and tables with a one-line purpose each, analytics layer first.Only allow-listed objects are shown.
describe_objects(names)“What are the columns, and what do they mean?”Reads real column names, types and descriptions from Postgres; optionally the view’s SQL definition.Stops the model inventing column names.
run_sql(query)Getting numbers: rankings, totals, drill-downs.Validates and runs one SELECT, returns up to 200 rows as JSON.Parsed with sqlglot; single SELECT; allow-listed objects; read-only session; 15s timeout; errors returned for retry.
search_news(query)Finding relevant news and research by meaning.Embeds the question and finds the closest articles with pgvector; keyword fallback.Read-only; returns source, date and url for citation.

A tool definition

# The docstring is what the LLM reads to decide when and how to call the tool.
@tool
def run_sql(query: str) -> str:
    """Execute ONE read-only PostgreSQL SELECT (CTEs allowed) against the allowed
    objects and return the result as JSON. At most 200 rows are returned; aggregate or
    ORDER BY ... LIMIT in SQL rather than pulling raw rows. If you get an ERROR, read it,
    fix the SQL and try again."""
    try:
        res = execute_select(query)          # parse → allow-list → read-only session
    except SQLValidationError as e:
        return f"ERROR (validation): {e}"    # errors go back to the LLM, not to the user
    return json.dumps(res)

Wiring the agent

model = init_chat_model("openai:gpt-4.1")          # any provider: change one string
agent = create_agent(
    model=model,
    tools=[list_objects, describe_objects, run_sql, search_news],
    system_prompt=SYSTEM_PROMPT + verified_examples,  # rules + few-shot SQL
    checkpointer=InMemorySaver(),                     # conversation memory per thread_id
)
agent.invoke({"messages": [{"role": "user", "content": question}]},
             {"configurable": {"thread_id": thread_id}, "recursion_limit": 30})
The LLM call flow

One question, three decisions

The agent is a loop. Each turn, the LLM sees the system prompt, the tool descriptions, the conversation so far and every tool result. It then makes one decision: call a tool (and which one, with what arguments) or answer. LangChain executes the tool, appends the result, and asks again.

Where accuracy comes from

The model reasons; your data layer makes it right

A general LLM knows finance, but nothing about your customers, your tables or your definitions. Its accuracy comes from what you put around it. Five levers do most of the work:

Failure you would see without itWhat prevents it in Customer360
✕ Queries a column that does not exist✓ describe_objects reads the real schema; errors are returned so it retries
✕ Adds USD and SGD together✓ mv_* views are already in SGD via ref_fx_rate
✕ Invents its own “rate impact” formula each time✓ One definition in mv_customer_rate_sensitivity and metric_catalog
✕ Makes up news or quotes stale facts✓ search_news returns real articles with source and url
✕ Runs a DELETE or reads addresses✓ SQL guard: SELECT only, allow-list excludes customer_profile, read-only session
✕ Answers “best portfolio” with an arbitrary method✓ Prompt guidance + age_band percentiles + a verified example query
Vectorization

Vectorize meaning, query facts

An embedding turns text into a list of 1,536 numbers so that texts with similar meaning sit close together. That is ideal for “find articles about higher rates hurting bonds”, and useless for “total AUM of customers over 65”, which needs exact arithmetic. Use one test for every piece of data:

Keep personal data out of embeddings. Names, emails and addresses are looked up exactly (ILIKE), and embeddings are sent to an external API. Embedding PII adds privacy risk and gives no search benefit.

Build it yourself

The order that works

Most failed agent projects start with the model. Start with the data instead:

  1. Write down 10 real questions.They decide which metrics you need. Here: investor type, best portfolio for age, Fed-hike impact.
  2. Build the semantic layer.Views with business labels over the raw tables; fix bugs in them first (this project found two).
  3. Pre-compute the hard metrics.Materialized views in one currency, with each metric defined once in a catalog and documented with column comments.
  4. Write a few narrow tools.Clear names and docstrings, typed arguments, and results the model can read (JSON with column names).
  5. Add guardrails before you add features.Read-only database role, SQL parsing, an allow-list, timeouts and row limits. Return errors to the model.
  6. Write the system prompt and verified examples.House rules, domain guidance, and question → SQL pairs you have run yourself.
  7. Vectorize only the free text.News, research, notes. Store embeddings next to the rows in Postgres with pgvector.
  8. Put a UI and an API around it.Fixed SQL for dashboards, the agent for open questions, and show “how I got this” so users can check the work.
  9. Test with your 10 questions every time you change something.Accuracy regressions come from data and prompt changes as often as from the model.
